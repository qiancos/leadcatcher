## 1. 一页纸摘要（TL;DR）

**一句话**：业务人员把聊天原文粘进来，Agent 在 5 秒内返回「手机号 / 行业 / 需求 / 预算 / 意向等级 / 风险备注」六个字段，线索进看板统一检索跟进，人工纠错回流成 Prompt 迭代依据。

**现状 → 目标**

| | 现在 | 用了之后 |
| --- | --- | --- |
| 单条线索整理 | 打开表格 → 复制 → 读对话 → 提炼需求 → 凭感觉判级 → 填 6 列 ≈ 3 分钟 | 粘贴 → 确认 ≤ 15 秒 |
| 判级标准 | 每人一套，因人而异 | 一份 rubric 写进 Prompt，全公司一个尺子 |
| 漏跟进 | 靠 Excel 自己记，容易忘 | 看板按「待跟进 + 意向」排序，红点提醒 |
| 复盘 | 无数据，只能讲感觉 | 准确率 / 无效占比 / Bad Case 分类可算 |

**成功标准（V1 验收线）**

1. 字段级提取准确率 ≥ 85%，意向分级准确率 ≥ 80%（30 条标注测试集）
2. 同手机号线索 100% 被识别为重复并提示
3. 广告 / 乱码 100% 归为「无效」
4. 单条线索人工处理耗时 ≤ 20 秒（基线 3 分钟，节省 ≥ 80%）
5. Demo 在线可访问，3 个页面无报错，配套 Prompt 库 + 迭代记录

**明确不做**：不接任何第三方渠道 API、不做自动触达/外呼、不做账号权限体系、不做客户 SOP 流程。（理由见 5.2）

## 2. 背景与问题

### 2.1 现状流程（As-Is）

营销同学每天的工作流：

```
① 收到消息   → ② 判断是不是线索 → ③ 复制到 Excel → ④ 读一遍提炼需求
（表单/私信/评论区/群聊，5~20 条/天，分散在 3~4 个入口）
     ↓
⑤ 凭经验判断"这个值不值得跟" → ⑥ 填 6 列（联系方式/行业/需求/预算/等级/备注）
     ↓
⑦ 排跟进优先级 → ⑧ 打电话/加微信 → ⑨ 回来改状态
```

### 2.2 痛点排序

| # | 痛点 | 具体表现 | 业务影响 | 优先级 |
| --- | --- | --- | --- | --- |
| P1 | **重复劳动** | 一条线索 2~4 分钟纯手工搬运，6 个字段逐个复制 | 20 条/天 ≈ 1 小时/天，全是低价值动作 | P0 |
| P2 | **标准不统一** | 老员工认为「问了价格」就是高意向，新人认为要「提到预算」才算 | 同一条线索两个人判级不同，跟进优先级失真 | P0 |
| P3 | **漏跟 / 漏记** | 漏打卡片、漏填表格、微信里翻不回去 | 直接损失成单机会，且无法归因 | P0 |
| P4 | **无法复盘** | 没有结构化数据，说不清"哪类线索质量差" | 投放/话术优化没有依据 | P1 |
| P5 | **结论无沉淀** | 判级标准在老人脑子里，人走了就没了 | 团队能力不可复制 | P1 |

> P1/P2/P3 是本项目的立身之本；P4/P5 是「为什么必须结构化落库」的答案，也是这个岗位真正想看的东西。

### 2.3 为什么现在是 LLM 能解

- 输入是**非结构化对话**，字段又是**短文本抽取**——这是 LLM 相对规则引擎有数量级优势、且不需要训练数据的典型场景。
- 字段少（6 个）、容错高（错了可人工改）、无强一致性要求（不是支付、不是库存），**失败成本可被人工兜底吃掉**，适合先上 V1。
- 判级标准可以用自然语言 rubric 固化进 Prompt，改 Prompt 即改标准，**不需要发版**——这正是"沉淀可复用 Prompt 资产"的价值。

## 3. 目标与指标

### 3.1 目标对齐

| 业务目标 | 产品目标 | 可量化指标 | V1 目标值 |
| --- | --- | --- | --- |
| 减少整理时间 | 一条线索只做 1 次粘贴 + 1 次确认 | 单条处理时长 | ≤ 20s（基线 180s） |
| 统一判级标准 | 意向分级由 rubric 决定，不由人决定 | 意向分级准确率 | ≥ 80% |
| 沉淀 Prompt 资产 | Prompt 版本化 + 指标回归 | 每次改 Prompt 有对照数据 | 100% 版本有记录 |
| 可演示可复盘 | 线上 Demo + 数据大盘 | 页面可用性 / 指标可读 | 3 页无报错 |

### 3.2 指标定义（口径必须唯一，否则复盘全是吵架）

| 指标 | 定义 | 计算方式 | 数据来源 |
| --- | --- | --- | --- |
| 提取成功率 | 关键字段（phone / industry / demand / intent）无错无漏的样本占比 | 正确样本 / 总样本 | 人工复核标记 |
| 字段级准确率 | 单字段判断正确的比例 | 单字段正确条数 / 总条数 | 人工复核标记 |
| 意向分级准确率 | `intent_level` 与人工判定一致的比例 | 一致条数 / 总条数 | 人工复核标记 |
| 无效线索占比 | AI 判「无效」的条数 / 总条数 | — | 系统统计 |
| 识别失败率 | `parse_status = failed` 的条数 / 总条数 | — | 系统统计 |
| 人工节省时间 | (基线耗时 − 现耗时) × 条数 | 抽样计时 20 条 | 手工计时 |
| Bad Case 率 | 提交了「识别错误」反馈的条数 / 总条数 | — | 反馈库 |

**关键设计**：为了让"准确率"可算，看板上每条线索除了「标记错误」，还必须有一个**「确认正确」**动作（一键，不进表单）。否则只有分子没有分母，指标永远算不出来。

### 3.3 非目标（V1 不做，且不影响验收）

- 不做线索质量的预测性建模（如"预计成单率"）
- 不做多轮对话式补全（追问客户"您预算多少"）
- 不做自动分配销售 / 排班 / 提醒推送

## 5. 范围与边界

### 5.1 In Scope（做什么，做到什么程度）

| 模块 | 做到什么程度 | 不做到什么程度 |
| --- | --- | --- |
| 输入 | 粘贴文本，单条 / 批量（≤20 条），≤8000 字/条 | 不做文件导入（Excel/CSV）、不做渠道对接 |
| AI 解析 | 固定 6 字段 JSON，失败可重试、可人工补录 | 不做多轮追问补全 |
| 意向分级 | 四级（高/中/低/无效），rubric 固定 | 不做细分打分（0-100）、不做行业定制规则 |
| 去重 | 手机号强重复 + 文本相似度弱提示 | 不做自动合并/自动删除 |
| 看板 | 筛选、搜索、排序、编辑、改状态、软删 | 不做多用户、不做权限、不做导出以外的报表 |
| 大盘 | 4 个指标 + 2 张图，7/14/30 天切换 | 不做自定义拖拽看板 |
| 反馈 | 字段级纠错 + Bad Case 分类 | 不做自动 Prompt 改写 |

### 5.2 Out of Scope（明确不做 + 理由）

| 不做 | 理由 | 如果要做的前置条件 |
| --- | --- | --- |
| 企业微信 / 小红书 / 抖音渠道 API 接入 | 每家都要审核、备案、OAuth、限流、字段映射，**占掉 70% 工期却只服务 1 个演示路径**；粘贴已能证明核心价值 | 先有稳定单渠道需求 + 明确的接入优先级 |
| 短信 / 外呼自动触达 | 涉及运营商资质、内容合规、投诉风控，是独立产品线 | 独立立项 |
| 账号权限体系 | V1 单账号使用，多角色会带来 RBAC、数据隔离、审计日志三重复杂度 | 有第二个真实使用者时再做 |
| 客户 SOP / 跟进日历 / 提醒 | 属于 CRM 范畴，本项目定位是"归集 + 分级"，不是 CRM | 线索归集稳定后再谈 |
| 线索自动分配 | 依赖组织架构与销售画像 | 依赖权限体系 |

### 5.3 假设与依赖

| # | 假设 | 若不成立的应对 |
| --- | --- | --- |
| A1 | 输入是中文对话文本，且包含客户自述信息 | 支持中英混排；纯英文降级为「需人工确认」 |
| A2 | LLM 单次调用 P95 < 15s，成本可忽略 | 换模型 / 加缓存 / 降级本地规则 |
| A3 | 业务人员愿意花 15 秒确认 | 提供「全部确认」批量动作 |
| A4 | Demo 数据为脱敏样例，不用真实客户数据 | 上线真实数据前需加加密存储与访问审计 |

### 5.4 一个必须讲清楚的取舍

> **V1 选「粘贴」而不是「接入」**：渠道接入是"集成工作量"，粘贴是"产品价值验证"。面试项目要在有限工期里证明的是**归集与分级的判断力**，不是 API 对接熟练度。所以把工期压在 Prompt 契约、分级标准、去重规则、反馈闭环这四件真正体现产品思维的事上。

## 6. 功能需求

> 每个需求都给出**规则 + 异常 + 验收**。标 🔴 的为 P0（不做完不能上线），🟡 为 P1（演示加分）。

### 6.1 线索录入 🔴

**FR-1.1 单条录入**
- 顶部常驻「+ 录入线索」入口 → 右侧抽屉（不跳页，保留看板上下文）
- 文本域，粘贴即用；底部实时显示字数 / 8000 上限
- 提交后 3 秒内出现"解析中"骨架态，不允许重复提交（按钮禁用 + 前端幂等锁）

**FR-1.2 批量录入**
- 切换「批量模式」，粘贴多段对话
- **切分规则**（按优先级）：`---` / `===` 分隔行 > 连续空行 > 「一行一条」开关
- 切分后显示**切片预览**：第 N 段 · 字数 · 首行摘要，可手动删除某片、合并相邻两片
- 上限 20 条 / 次；超过则提示"本次 24 段，仅提交前 20 段"
- 并发 3 条跑，结果逐条回填（不等全批量，早出结果早跟进）
- 允许部分失败：失败的条目单独显示「重试」，不影响其他条

**FR-1.3 异常与限制**

| 场景 | 系统行为 |
| --- | --- |
| 空输入 / 全空白 | 禁用提交，提示「请粘贴对话内容」 |
| 字数 < 10 | 允许提交，但标注「内容过短，解析结果可能不可靠」 |
| 字数 > 8000 | 阻止提交，提示「超出 8000 字，请截取关键片段（建议保留客户诉求与联系方式部分）」 |
| 网络/服务异常 | 保留输入内容，提供「重试」；不自动重试以免重复入库 |
| 完全相同的文本重复提交 | 命中 `text_hash`，提示「该内容已录入过（创建于 X 月 X 日）」，可选择仍要录入 |

**验收**
- 粘贴 12 段对话 → 切分结果为 12 段 → 8 秒内全部返回结果
- 中途断网 → 输入不丢失，恢复后可重试
- 同一文本重复提交 → 出现幂等提示，且不产生第 2 条记录（除非用户确认）

### 6.2 AI 解析（核心）🔴

**FR-2.1 输出契约（固定 JSON，不可增删字段）**

```json
{
  "phone": "13800001234",
  "customer_industry": "餐饮",
  "demand": "下月新店开业，想做本地生活平台投放，希望能到店聊方案",
  "budget_hint": "预算 3 万左右",
  "intent_level": "高",
  "risk_note": null
}
```

| 字段 | 类型 | 格式 / 枚举 | 必填 | 无法判断时 |
| --- | --- | --- | --- | --- |
| `phone` | string \| null | 11 位大陆手机号，纯数字 | 否 | `null`（**禁止编造**） |
| `customer_industry` | string \| null | ≤10 字，优先命中行业白名单① | 否 | `null` |
| `demand` | string | ≤60 字，客户视角的诉求摘要 | **是** | 空 → 判 `failed` |
| `budget_hint` | string \| null | ≤40 字，**原文摘录**，不做换算 | 否 | `null` = 对话未提预算 |
| `intent_level` | enum | `高` / `中` / `低` / `无效` | **是** | 非法值 → 判 `failed` |
| `risk_note` | string \| null | ≤40 字，仅记录异常 | 否 | `null` |

> ① 行业白名单（V1，12 类）：餐饮、零售、教育、美业、房产、汽车、医疗、金融、本地生活、制造、互联网、其他。

**FR-2.2 抽取约束（写进 System Prompt 的硬规则）**

1. **只允许使用对话中明确出现的信息**，禁止推断、补全、"合理猜测"。
2. `phone` 只提取**客户本人自报**的号码；对方业务员的号码、群号、地址电话一律不取。
3. 没有提到预算 → `budget_hint = null`，**不允许**输出"预算充足""预算不明"这类臆断。
4. 广告推销 / 同行探价 → `intent_level = 无效`，`demand` 写清其推销内容（便于识别刷量）。
5. `demand` 用客户口吻写，不写"客户希望…"的第三人称。
6. 只输出 JSON，不带 markdown 代码块、不带解释文字。

**FR-2.3 意向分级 Rubric（V1 唯一标准，见 10.2 完整版）**

判定顺序：**无效 → 高 → 中 → 低**，命中即短路。理由：误把广告判成高，业务要白打 3 通电话；误把高判成中，只是晚一天跟进——**成本不对称，所以宁可偏保守地排除无效，也不轻易抬级**。

**FR-2.4 手机号防幻觉（正则二次校验）**

- 先取 LLM 输出 → 用 `(?:\+?86[-\s]?)?1[3-9]\d{9}` 二次校验
- 校验通过：归一化为 11 位数字（去 `+86`、去空格/横线、全角转半角）
- 校验不通过：**以正则为准**，若原文中能正则命中则用正则结果；原文也无则置 `null`
- 原文命中的原始片段存入 `phone_raw`（审计用，便于排查"到底哪里抽错了"）

**FR-2.5 失败处理（必须显式设计，否则数据会脏）**

| 失败类型 | 系统行为 | 落库 |
| --- | --- | --- |
| LLM 超时（>30s）/ 5xx | 自动重试 1 次（退避 2s）；再失败 → 标记 `failed` | 是，保留 `raw_text` |
| 返回非 JSON | 用「请仅输出 JSON」二次修复重试 1 次；仍失败 → `failed` | 是 |
| JSON 合法但缺必填字段 | 判 `failed`，错误原因写 `parse_error` | 是 |
| 内容过短 / 乱码 | 不判 `failed`，判 `intent_level = 无效` + `risk_note = "内容过短无明显诉求"` | 是，标为无效 |

> **原则：解析失败绝不丢数据。** 失败的线索仍入库，在看板置顶为黄色「待补录」，业务可手填或重试。这是"宁可多一条脏数据，不可丢一条商机"的产品选择。

**验收**
- 30 条测试集中，正常对话的关键字段准确率 ≥ 85%
- 手工塞入含「对方业务员手机号」的对话 → 不误取业务员号码
- 构造 LLM 返回非法 JSON → 系统重试后标记 `failed`，原文完整保留
- 输入 8000 字长文 → 正常解析，无报错

### 6.3 线索去重 🔴

| 类型 | 触发条件 | 系统行为 | 用户可做 |
| --- | --- | --- | --- |
| **强重复** | 归一化后手机号完全相同（不限时间窗口） | 入库但 `is_duplicate=1`，`duplicate_of` 指向最早一条；提交时即时提示"该手机号已有线索（3 天前，意向：中）"；列表打橙色「重复」角标 | 点「不是重复」（解除标记）/ 直接删除本条 |
| **疑似重复** | 一方无手机号 或 手机号不同，且 `demand` 的 3-gram Jaccard ≥ 0.85，且在 7 天内 | 仅在录入结果里提示"疑似与 #123 重复"，**不写库、不占标记** | 忽略，或手动删除 |

**规则细节**
- **不自动删除、不自动合并**：手机号可能同属一家公司（老板 / 采购 / 前台），自动合并会吃掉真实商机。
- 提示文案必须写"疑似"，不能写"已重复"。
- 相似度用字符 3-gram Jaccard（对 ≤60 字摘要足够，且无需额外依赖）；阈值 0.85 为初值，**验收时用 10 组构造样本校准**，目标 precision ≥ 90%、recall ≥ 70%。

**验收**
- 同手机号录入 2 次 → 第 2 次出现重复提示，且标记正确
- 同手机号但换了角度描述 → 仍判强重复
- 两家不同客户的相似需求（如同模板广告）→ 不误判为强重复
- 删除原始线索后，重复标记悬空 → 自动回落为普通线索（`duplicate_of` 置空）

### 6.4 线索看板 🔴

**列表字段**：录入时间 / 手机号（脱敏）/ 客户行业 / 需求摘要 / 意向等级 / 跟进状态 / 操作

**默认排序**：`待跟进` 优先 → 意向权重（高 > 中 > 低 > 无效）→ 时间倒序。业务打开就能从上往下打。

**数据状态模型（两个独立维度，不要混成一个字段）**

```
parse_status  : success | failed（failed 可重试 → success）
follow_status : pending（待跟进）⇄ followed（已跟进）
                pending / followed → invalid（已放弃，需二次确认）
                invalid → pending（可恢复）
```

`is_duplicate` 是第三个独立布尔标记。三者互不覆盖，这样"AI 没解析出来"和"人判断这单不跟"不会被混为一谈，统计口径才不会打架。

**筛选与搜索**

| 筛选项 | 形态 | 说明 |
| --- | --- | --- |
| 意向等级 | 多选 chip（高/中/低/无效） | 默认全选 |
| 跟进状态 | 多选 chip | 待跟进 / 已跟进 / 已放弃 |
| 时间 | 快捷项（今天/近 7 天/近 30 天）+ 自定义区间 | 按 `created_at` |
| 搜索 | 单输入框 | 匹配手机号（支持后四位模糊）/ 需求摘要 / 行业 / 原文全文 |
| 仅看重复 / 仅看解析失败 | 开关 | 排查用 |

**操作**

| 操作 | 交互 | 规则 |
| --- | --- | --- |
| 查看详情 | 点行 → 右侧抽屉 | 上半屏原文，下半屏解析结果**左右对照高亮**（演示重点） |
| 编辑 | 抽屉内「编辑」 | 可改所有解析字段（含手机号、等级），原文只读；改动写 `updated_at`，人工改过的字段标「人工修正」 |
| 标记已跟进 | 行内按钮 1 次点击 | 即时生效，无弹窗；可再次点「撤销」 |
| 标记放弃 | 行内更多菜单 | 二次确认（防误点） |
| 删除 | 行内更多菜单 | 软删（`deleted_at`），7 天内可恢复；列表不显示 |
| 重试解析 | 仅 `failed` 行显示 | 重新调用 LLM，成功后覆盖字段 |

**验收**
- 组合筛选（意向=高 + 状态=待跟进 + 近 7 天）结果正确
- 搜索手机号后四位命中对应线索
- 标记已跟进后刷新页面状态不丢
- 删除后列表消失，恢复后可回来
- 列表 500 条数据渲染 < 1s，翻页无白屏

### 6.5 数据大盘 🟡

| 模块 | 内容 | 口径 |
| --- | --- | --- |
| 指标卡 | 线索总量 / 有效线索 / 待跟进 / 解析失败 | 有效 = `intent_level ≠ 无效` 且 `parse_status = success`；失败单独计数，**不计入有效** |
| 饼图 | 意向等级分布 | 分母 = 有效线索数；提供"含无效"切换 |
| 折线 | 每日新增趋势 | 7 / 14 / 30 天切换，按自然日（UTC+8）零填充，无数据的日子补 0 |
| 柱状 | 解析失败数（按天） | 与折线同图切换，或独立小图 |
| 一致性提示 | 若「AI 判高」与「人工判无效」冲突超 5%，顶部提示"判级一致性异常，建议检查 Prompt" | 这是给复盘用的哨兵，演示时很好讲 |

**口径取舍（必须写死，否则每周复盘都要吵一次）**：`有效线索` 只看 AI 判级（`intent_level ≠ 无效` 且解析成功），**不随人工「已放弃」动作增减**。因为大盘的第一用途是监控 AI 质量，如果人工一改状态数字就变，就永远不知道是模型变好了还是人工变勤快了。真正反映"今天要打几个电话"的是 `待跟进` 卡，它在指标卡里独立展示。

**验收**
- 录入 10 条（3 高 / 2 中 / 3 低 / 2 无效）→ 饼图比例与数字完全一致
- 切换 7/30 天 → 折线横轴与数据同步
- 页面无数据时显示空态图，不显示 JS 报错

### 6.6 反馈与迭代 🔴（岗位核心亮点）

**FR-6.1 双动作复核**

每条线索都有两个并列动作，缺一不可：
- ✅ **确认正确**（一键，无表单）→ `human_verified = correct`
- ✏️ **标记识别错误** → 打开纠错抽屉 → `human_verified = wrong`

> 没有「确认正确」这个动作，准确率就永远没有分母。这一条是 PRD 里最容易被漏、但直接决定"能不能复盘"的设计。

**FR-6.2 纠错表单**

| 字段 | 形态 | 必填 |
| --- | --- | --- |
| 哪些字段错了 | 多选：手机号 / 行业 / 需求摘要 / 预算 / 意向等级 / 整体（漏识别） | 是 |
| 正确值 | 与被勾选字段联动的输入框 | 是（至少填 1 项） |
| 错误归因 | 单选：漏提取 / 提取错 / 判级偏差 / 摘要失真 / 格式失败 / 其他 | 是 |
| 备注 | 文本 | 否 |

**FR-6.3 Bad Case 分类（固定 taxonomy，否则聚不起来）**

| 编号 | 分类 | 典型样例 |
| --- | --- | --- |
| BC-1 | 手机号漏提取 / 误提取 | 客户说"加我尾号 8000"，模型没补全；误取业务员号码 |
| BC-2 | 意向判断偏差 | 问了价格就判「高」，但客户明确说"先看看" |
| BC-3 | 需求摘要失真 | 把客户的抱怨当需求；漏掉关键时间/场景 |
| BC-4 | 行业误判 | "做抖音团购的"判成互联网，实际是餐饮 |
| BC-5 | 重复误判 | 不同客户被判强重复 |
| BC-6 | 格式/解析失败 | JSON 不合法、超时 |

**FR-6.4 复盘机制（每周一次，30 分钟）**

```
① 拉上周数据：准确率 / 无效占比 / 失败率
② 从反馈库导出去重后的 Bad Case，按 BC-1~6 归类，取 Top 3
③ 定位是 Prompt 问题还是规则问题（如手机号 → 正则兜底；判级 → rubric 措辞）
④ 改 Prompt → 版本号 +1 → 在固定测试集（30 条）上回归
⑤ 记录：版本 / 改动点 / 旧指标 / 新指标 / 结论
```

**验收**
- 对 1 条线索标记错误 → 反馈库出现 1 条记录（含字段、正确值、归因）
- 对 1 条线索点确认正确 → `human_verified = correct`，可被统计
- 反馈列表可查看、可关闭（status: open → closed）

## 8. 数据模型

```sql
-- 线索主表
leads(
  id            INTEGER PRIMARY KEY,
  raw_text      TEXT NOT NULL,          -- 原文，永不可改
  text_hash     TEXT NOT NULL,          -- sha256(raw_text)，幂等去重
  phone         TEXT,                   -- 归一化 11 位
  phone_raw     TEXT,                   -- 原文中的原始片段（审计）
  customer_industry TEXT,
  demand        TEXT,
  budget_hint   TEXT,
  intent_level  TEXT NOT NULL,          -- 高/中/低/无效
  risk_note     TEXT,
  parse_status  TEXT NOT NULL,          -- success/failed
  parse_error   TEXT,                   -- 失败原因
  prompt_version TEXT NOT NULL,         -- 解析时使用的 Prompt 版本，用于 A/B
  is_duplicate  INTEGER DEFAULT 0,
  duplicate_of  INTEGER,
  follow_status TEXT DEFAULT 'pending', -- pending/followed/invalid
  human_verified TEXT DEFAULT 'unchecked', -- unchecked/correct/wrong
  created_at    DATETIME,
  updated_at    DATETIME,
  deleted_at    DATETIME
)
INDEX: (phone), (intent_level, follow_status), (created_at), (text_hash)

-- 反馈库
feedbacks(
  id, lead_id, wrong_fields TEXT(JSON), correct_values TEXT(JSON),
  error_category TEXT, note TEXT, status TEXT DEFAULT 'open', created_at
)

-- Prompt 版本表（复盘的地基）
prompt_versions(
  id, stage TEXT,            -- extract/intent
  version TEXT,              -- v1/v2
  content TEXT,
  activated_at DATETIME,
  note TEXT
)

-- 评测记录（P1，用于版本对比）
eval_runs(
  id, prompt_version, dataset_size, field_accuracy TEXT(JSON),
  intent_accuracy REAL, failed_count INTEGER, created_at
)
```

> `prompt_version` 打在每条线索上是关键设计：有了它，才能回答"v2 比 v1 好在哪"，而不是凭感觉说"我觉得改了之后更准了"。

## 10. Prompt 设计规范（产品资产，不算代码）

### 10.1 设计原则

| 原则 | 具体做法 | 为什么 |
| --- | --- | --- |
| 角色 + 任务边界 | 明确"你是营销线索分析助手，只做抽取与分级，不做建议" | 防止模型输出"建议尽快联系"这类废话 |
| 字段级约束 | 每个字段给类型、长度上限、缺失时填 `null` | 直接决定 JSON 是否可解析 |
| 禁止编造 | "对话中未出现的信息一律为 null，禁止推测" | 幻觉是这类场景的第一杀手 |
| few-shot | 2 个正例（正常咨询）+ 2 个反例（广告/模糊咨询） | 比写 500 字规则更能校准边界 |
| 分级 rubric 内嵌 | 四级判定条件 + 每级 2 个正反例 + 判定顺序 | 标准统一的核心 |
| 输出约束 | "只输出 JSON，不要 markdown 代码块" + `response_format: json_object` | 双重保险 |
| 版本化 | 每次改动必须升版本号并写变更说明 | 复盘基线 |

### 10.2 意向分级 Rubric（V1 正式版）

| 等级 | 判定条件（按顺序短路，命中即停） | 一句话自测 | 正例 | 反例 |
| --- | --- | --- | --- | --- |
| **无效** | ① 广告/推销/同行探价 ② 乱码、纯表情、无意义字符 ③ 非营销咨询（投诉、问路、找客服） | "这条不该进线索池" | "我是做代运营的，你们老板在吗" | "这个多少钱" |
| **高** | ① 有明确需求（要什么 + 时间/场景） ② 有购买信号（问价、要方案、要上门、要案例） ③ 有可用联系方式 | "现在就打电话，他会接并且愿意聊" | "下月新店开业，想做本地投放，预算 3 万，加我 138…" | "先了解一下行情" |
| **中** | 有需求方向，但缺 ② 购买信号 或 缺 ③ 联系方式 | "值得挖一轮，但要先问清楚" | "我们公司想投点广告，一般怎么收费" | "我朋友也做这个" |
| **低** | 泛泛咨询 / 比价观望 / 明确表示不着急 / 已在别家但还在闲聊 | "现在跟只会被当骚扰" | "先看看，有需要联系你" | "预算 3 万，明天来聊" |

**边界裁决规则**

1. 有预算 + 有时间 + 无联系方式 → **中**（不可电话触达，但可留言）
2. 无预算 + 有时间 + 有联系方式 + 明确需求 → **中**（预算可通过沟通解锁）
3. 客户明确说"不着急/再看看" → 最高判 **低**，不能被前面的话术抬上去
4. 同一条里既有广告又有真实需求（如"我是做代运营的，你们要不要投"）→ 判 **无效**，`risk_note` 注明"疑似同行"
5. 无法判断 → 判 **低** 并写 `risk_note`，不要判高（成本不对称）

### 10.3 版本管理机制

| 版本 | 改动 | 触发 Bad Case | 测试集指标 |
| --- | --- | --- | --- |
| v1 | 首版 rubric + 4 few-shot | — | 待回归 |
| v2 | 增加手机号"只取客户自报号码"约束 | BC-1 × 4 | 待填 |
| v3 | 判级改为"无效优先短路" | BC-2 × 5 | 待填 |

> 每次迭代只改**一个变量**，否则无法归因。这是从"改了感觉好一点"到"有数据支撑"的分水岭。

## 11. 技术方案

```
┌──────────────┐      HTTPS      ┌──────────────────┐
│ Vue3 + Vite  │ ──────────────► │ FastAPI          │
│ Element Plus │                 │  ├─ /leads 路由  │
│ ECharts      │ ◄────────────── │  ├─ 解析服务     │
└──────────────┘      JSON       │  ├─ 去重服务     │
                                 │  └─ 统计服务     │
                                 └────────┬─────────┘
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    ▼                     ▼                     ▼
              SQLite(单文件)        LLM API(DeepSeek)      正则校验层
                                   json_object 模式       (手机号兜底)
```

| 决策 | 选择 | 理由 | 放弃的方案及原因 |
| --- | --- | --- | --- |
| 前端 | Vue3 + Element Plus | 后台表格/表单开箱即用，AI 生成代码质量高 | React 也行，但 Element 的 table/filter 能省 1 天 |
| 后端 | FastAPI | 自动 Swagger 文档（演示时可直接给面试官看接口）、异步调用 LLM 顺手 | Express 需要自己搭校验与文档 |
| DB | SQLite | 零部署、单文件可备份、Demo 够用 | PostgreSQL 在免费实例上多一层运维 |
| LLM | DeepSeek（`response_format: json_object`） | 中文对话理解强、JSON 模式稳定、成本低 | 豆包可作备选（同 OpenAI 协议，改 base_url 即可） |
| 部署 | Render（含持久盘）或 Railway | 一键部署 + 自动 HTTPS | 纯静态 Vercel 无法挂 SQLite |

**关键实现说明**
- LLM 调用统一走 OpenAI SDK（`base_url` 指向 DeepSeek），换模型只改环境变量
- 解析结果**先校验后入库**：JSON Schema 校验 → 手机号正则 → 枚举校验 → 写库
- `raw_text` 永不被覆盖，任何 AI 结果都可追溯、可重放（这决定了能不能事后调 Prompt）

**环境变量**

```
LLM_API_KEY=xxx
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
ADMIN_TOKEN=xxx        # V1 单口令控制台入口
DB_PATH=./data/leads.db
```

## 15. 复盘机制（每周 30 分钟）

**固定模板**

```
周期：第 N 周
数据：准确率 __% ｜ 无效占比 __% ｜ 失败率 __%
Bad Case Top3：
  BC-1 × __（例：尾号 8000 未补全）
  BC-2 × __（例：问价即判高）
动作：Prompt v__ → v__，改动 ______
回归：AC-2 准确率 __% → __%（同测试集）
结论：______（有效 / 无效，是否回滚）
```

**三条纪律**
1. 每次只改一个变量，否则无法归因
2. 测试集冻结，改样本必须在记录里注明「样本变更」
3. 指标变差要写清楚是"改了 Prompt"还是"改了标注标准"——这两种"变差"含义完全不同

## 附录 B：常见追问与答法（自用，交付时可删）

| 追问 | 答法要点 |
| --- | --- |
| 为什么不做渠道接入？ | 渠道接入是集成成本，粘贴是价值验证；Demo 周期内优先证明"归集+分级"的判断力。已在 5.2 写明前置条件。 |
| 判级为什么不用 0-100 分？ | 分级可解释、业务能对齐；分数看起来精细，但不同人对 72 分和 78 分的理解不一致，反而更难统标。 |
| 准确率怎么算的？ | 30 条标注测试集 + 人工复核双动作（确认正确/标记错误）。所以看板必须有"确认正确"按钮，否则没分母。 |
| LLM 幻觉怎么办？ | 三层：Prompt 禁止编造 + 正则二次校验（以正则为准）+ 失败标记入库人工兜底。 |
| 怎么证明变好了？ | Prompt 版本化 + 每条线索记 `prompt_version` + 固定测试集回归，版本间对比准确率。 |
| 重复线索为什么不自动合并？ | 同号可能是老板/采购/前台，自动合并会吃掉商机；只提示不合并，把决策权留给人。 |
| 如果给你两周？ | 加渠道接入（先接 1 家）、来源维度分析、成单结果回填做"判级-成单"相关性验证。 |
