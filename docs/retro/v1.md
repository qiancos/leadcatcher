## 0. 一句话结论

V1 在 30 条自建样本上拿到很好的分数，但**这个分数证明的是「标准落地了」，不是「模型很聪明」**——
样本与 rubric 高度同构，规则引擎当然能对上。真正有价值的发现是下面第 3 节的三条，
以及第 4 节里那些只有真跑起来才会暴露的 bug。

## 3. 三件真正涨经验的事

### 3.1 指标定义错了，数值再准也没用

首轮跑完，需求摘要只有 **36%**，看着像功能失灵。逐条拉明细才发现是尺子的问题：

- 标注写「希望到店沟通」，原话是「能到店聊吗」——改写版摘要按 3-gram 字面匹配天然过不了；
- 这不是抽取失败，是**判定方式与任务性质不匹配**。

改成「关键信息点覆盖率」（每条约 2–4 个人工信息点，命中 ≥ 60% 记对）后回到 95%，
且唯一的失败样本（C29 长文）是**真的抽不全**，不是被误杀。

> 教训：先确认"这个数是量什么"，再讨论"这个数好不好看"。

### 3.2 规则和模型的边界，得靠具体样本摸出来

C12「我们做**贷款中介**的，需要精准获客，预算充足」——
号码被误判成"业务员号码"剔除了，因为 `中介` 被我放进了业务员关键词。

这是典型的**词表过度泛化**：`中介` 在"业务员/渠道"语境里是干扰项，在"贷款中介/房产中介"里
却是客户自己的行业。修法是把 `中介` 从业务员词表里拿掉，改用更强的角色词
（业务员 / 客户经理 / 渠道 / 客服 / 座机 / 热线）。

> 教训：规则引擎的每一个关键词都在**用精度换召回**，必须一条条看样本，不能凭直觉堆词。

### 3.3 "解析失败也入库" 不是偷懒，是产品选择

给演示数据里特意留了一条 `parse_status = failed` 的样本，看板置顶显示「失败 / 待跟进」，
详情页可以「重试解析」，原文完整保留。

理由很朴素：**宁可多一条待补录的脏数据，不可丢一条商机。** 把一个客户的对话弄丢了，
业务永远不知道损失了什么；多一条待补录的记录，最差也只是多点一次鼠标。

## 4. 开发期暴露的 bug（都已修）

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 预算字段吸进了前文：「平台的推广，预算大概3万左右，方便的话加我」 | 一条全局正则从左往右扫，最短匹配点落在了关键词前面 | 改成**按分句取**，先切句再找含"预算"且有数字的那句 |
| 2 | 需求摘要里出现完整手机号 | 摘句时把联系方式句一起带进去了 | 摘要生成后抹掉号码形态；纯联系方式句（"方便的话加我…详聊"）直接丢弃 |
| 3 | `--reset` 之后第一条线索是 #31 | SQLite `AUTOINCREMENT` 的序列不随 `DELETE` 归零 | 重置时同步 `DELETE FROM sqlite_sequence` |
| 4 | 看板「跟进状态」列被右侧固定列压住 / 意向标签竖排成三行 | 表格固定列总宽超过容器；`.intent-chip` 没设 `nowrap` | 收窄列宽、去掉 `fixed`、给 chip 加 `white-space: nowrap` |
| 5 | 删除原始线索后，被标记为重复的线索悬空指向已删 id | 只做了软删，没处理引用 | 删除时把 `duplicate_of = 该 id` 的记录回落成普通线索 |

前 2 条是**业务正确性** bug（会误导人），后 3 条是**演示体验** bug（会显得不专业）。
两类都必须修，但优先级不同：业务正确性 > 体验 > 视觉。
